# QQ群智能守护者 (GroupGuardian) – 项目概述

**累计反思 40 次**

## 1. 项目简介

GroupGuardian 是面向 AstrBot（Python 3.10+）的综合 QQ 群管理插件，提供 28 项群管功能、AI/LLM 审核、SQLite 词库与日志、OCR/视觉审核、防刷屏、名片监控、自适应词库学习及 AstrBot Dashboard WebUI。支持 OneBot 生态（NapCat、LLOneBot 等），通过 `register_web_api` 复用 Dashboard 鉴权，不启动独立 Web 服务。

## 2. 技术栈与结构

- 存储：`group_guardian.db`（运行时日志/状态）与 `lexicon.db`（外置词库）
- 审核：Aho-Corasick/纯 Python Trie + 正则回退 + LLM 二审；支持上下文、嵌套消息、Base 编码、OCR/GIF/表情和全量 AI 模式
- 主要模块：`main.py` 入口；`commands.py` 命令；`moderation.py` 审核；`anti_flood.py` 刷屏；`card_monitor.py` 名片；`appeal.py` 申诉/解禁；`membership.py` 入群；`storage.py` 持久化；`web.py` Web API；`llm_tools.py` AI 工具；`onebot.py` 协议适配；`scheduler.py` 调度；`pages/dashboard/` 前端
- 可选同步组件涉及本地 SQLite、远端 API、审计日志和远程动作；必须按分布式状态机审查，不能只看 HTTP 200 或测试总数。

## 3. 开发与审查约定

1. **Mixin/MRO 与全入口**：`Main` 继承清单决定运行时 API。迁移方法须检查直接/间接 `self.xxx`、MRO 覆盖、命令/WebUI/后台入口、初始化顺序；命令优先委托共享业务实现，避免重复处罚。
2. **高风险操作**：撤回、禁言、踢人、解禁、学习和 WebUI 确认须重新校验权限、状态、二次确认、幂等性和审计。底层副作用明确成功后才可回执成功；`None`、异常、未知返回不得默认成功。
3. **远程动作状态**：拉取→执行→回执必须区分 `pending/processing/succeeded/retryable_failed/permanently_failed`；参数错误进失败/死信，网络或平台临时错误可重试，重复执行应安全且有退避、告警和审计。
4. **稳定关联**：复核、日志、同步和动作优先使用审核 ID、消息 ID、事件 ID 等持久化唯一标识。群、用户、文本、时间只能辅助匹配；0 个或多个候选均禁止猜测。集合键不得用单值字典覆盖。
5. **审核控制流**：通过词、拒绝词、通用词库、广告规则、LLM 和搜索 fallback 的优先级须显式定义。外部搜索失败、工具缺失、空/畸形结果、复审解析失败或证据不足均转人工，不能擅自放行/拒绝；未启用新功能不得跳过旧审核链路。
6. **外部内容不可信**：搜索结果、网页摘要和用户输入必须与系统指令隔离；限制查询数、单条/总长度、token、耗时和并发。统一 deadline 覆盖查询、拼接、二审和日志，超时任务应取消，避免成本放大。
7. **异步协议**：含 `yield` 的 `async def` 是异步生成器，必须 `async for`；事件循环内禁止阻塞网络/文件/数据库调用，必须异步客户端或 `asyncio.to_thread`、超时和取消。测试替身保持同一返回协议。
8. **协议与脏数据**：OneBot `comment`、引用块、拼入原文及 `[图片]` 占位符可能非用户输入；审核前剥离并区分文本重复检测与消息频率统计，覆盖引用、嵌套、图片和多协议差异。
9. **配置与 Schema**：新增开关/别名同步 schema、README、帮助、群级覆盖和旧配置兼容；测试全局/单群开关组合、非法值、默认关闭。所有数组 JSON Schema 必须有合法 `items`；按工具名和真实宿主协议回归，不依赖声明索引。
10. **同步与安全**：同步实体须闭合“读取→序列化→push→远端存储→pull→本地写回”，明确唯一键、版本、冲突、删除、重试和幂等；敏感字段采用正向 allowlist，禁止传输凭据、完整消息或未脱敏响应。审计记录须包含操作者、目标、状态前后、结果、失败原因和关联 ID。
11. **启动自检**：重复插件目录检测属于诊断而非自动治理；日志须含稳定插件 ID、版本、全部路径和处理建议。检查宿主加载时序、缺失/损坏 metadata、权限、符号链接、大小写和性能；不得误称已阻止重复加载。
12. **Issue 研判与重复检测**：需求用 `question`+`documentation`，新增功能 `enhancement`，缺陷 `bug`，绕过审核/提权/漏审倾向 `high`；重复结论须有可审计候选和置信度（低于 0.7 不输出），不能凭相似编号或关键词下结论。

## 4. 近期重点经验

- 入群审核的网页搜索是“证据增强”而非事实或结论；搜索内容不可改变提示词和输出协议，所有降级原因应可审计。搜索状态必须贯通持久化、Dashboard、人工处理、重试和唯一审核 ID。
- 远程 `unban` 等动作若吞掉 OneBot 异常、客户端为空或 API 失败，却统一返回成功，会使服务端永久消费失败动作；应原样传播明确失败，并横向检查其他动作。
- 同步客户端的大规模重构需审查旧客户端/服务端兼容、字段 allowlist、双向冲突、重复 push/pull、部分成功、数据库锁和审计闭环；“无 secrets 测试”不能替代这些证据。
- 同步恢复不能遗漏 `suggestions` 等实体；不能用群号+用户+文本前缀绑定重复记录。多实例必须使用持久化、唯一且不可预测的 client ID，并验证初始化、隔离和重建行为。
- `asyncio.create_task` 仍运行在事件循环；阻塞式 HTTP 会拖慢全插件。后台同步须有取消、互斥、退避和超时。
- 搜索、同步、远程动作和自动学习都应限制资源并默认失败安全；“测试总数通过”不能替代真实路由、权限失败、平台失败、并发、超时、重复和端到端测试。

## 5. 质量底线

高风险审核和自动动作默认关闭或人工确认；失败不得伪装成功，无法判断不得等同拒绝或放行。任何自动撤回、禁言、踢人、解禁、名片还原、学习和远程同步都应保留稳定关联、状态迁移、权限校验、幂等处理和可审计结果。文档、CHANGELOG、配置、迁移和测试须随行为变更同步；审查结论应区分“未发现可复现缺陷”和“已证明生产安全”。
