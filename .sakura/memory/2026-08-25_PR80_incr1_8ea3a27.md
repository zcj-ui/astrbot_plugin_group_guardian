## 1. 审查质量评估

### 覆盖度

本次审查抓住了核心安全与可靠性目标：

- 搜索默认关闭，避免未经配置就引入外部依赖；
- 只有初审明确要求 `search` 时才调用搜索；
- 搜索失败、复审解析失败或证据不足时转人工，而不是擅自通过或拒绝；
- 保留本地规则路径；
- 对查询数量和总时间预算进行限制；
- 测试覆盖了查询缺失、提示词注入、单次失败和超时等关键场景。

这些结论与该提交“强化网页搜索 fallback”的意图基本一致，9/10 且 approve 总体合理。

但由于审查类型是增量审查，仍可能遗漏以下问题：

1. **外部搜索工具的真实调用协议**
   - 是否正确处理 AstrBot `web_search_tavily` 的实际返回结构、异步协议和异常类型；
   - 工具不存在、返回 `None`、返回空列表、返回 malformed JSON 时是否都能进入人工审核；
   - 是否依赖工具注册顺序或不稳定的内部字段。
   
   项目记忆明确强调过 AstrBot 工具 Schema 和异步生成器问题，这类风险不能仅由单元 mock 覆盖。

2. **总时间预算是否真正覆盖完整链路**
   - 搜索调用本身之外，查询循环、结果拼接、第二次 LLM 调用和日志记录是否共享同一个 deadline；
   - 单个查询超时后是否仍可能阻塞总流程；
   - 第二次 LLM 审核是否有独立超时和取消机制。
   
   “测试总时间预算”是积极信号，但需要确认测试测的是实际生产调用路径，而不是仅测试一个封装函数。

3. **证据隔离仍需关注**
   - 当前测试覆盖了外部证据提示注入，但应进一步确认搜索结果是否始终作为不可信数据传入；
   - 搜索结果中的指令是否可能改变二审的输出格式、触发工具调用或覆盖系统提示；
   - 是否限制证据条数、单条长度和总字符数，避免超长结果导致上下文耗尽或成本失控。

4. **多入口和状态闭环**
   - Dashboard 展示、后台审核、人工处理是否都能识别 `search`、`manual` 或“证据不可用”等新状态；
   - 审核失败后是否保留足够的审计信息，并且不会重复执行搜索或处罚；
   - 人工处理入口是否仍能通过唯一审核 ID 关联原始请求，而不是依赖群、用户和内容猜测。

5. **配置兼容性**
   - 新增全局/分组配置的默认值、旧配置读取和异常值修正是否完整；
   - `max_queries` 的范围限制是否同时在配置加载、Dashboard/API 和运行时执行层生效；
   - 全局关闭与单群开启、全局开启与单群关闭等组合是否都有明确语义和测试。

### 准确度

没有主要评论，因此不存在明显误报或严重程度标记问题。将结果评为 approve 是合理的，尤其是该提交的核心安全策略是“失败转人工”，而不是“失败时自动放行”。

不过，9/10 可能略偏乐观。若测试主要是单元测试而没有覆盖：

- 真实 AstrBot 工具适配；
- 实际异步调用协议；
- 配置/API/后台页面到审核执行的完整链路；
- 外部工具不存在或返回异常结构；
- 并发请求和重复审核；

则更稳妥的评价应是“实现方向正确，但集成风险尚未完全消除”，而不是接近满分。

### 完整性

对变更意图的理解是充分的：该提交不是单纯增加搜索，而是修正“搜索不可用时如何降级”的控制流。

## 2. 发现的模式

### 代码模式

- **显式状态驱动**：初审结果从布尔值扩展为 `accept` / `reject` / `search`，比隐式真假值更适合表达多阶段审核。
- **失败安全**：外部依赖失败后进入人工审核，属于审核场景中更安全的 fail-closed 策略。
- **分阶段日志**：初审、搜索、证据复审分别记录，但不记录完整搜索片段，有利于审计与隐私控制。
- **预算约束**：查询数量和总耗时受到限制，说明已考虑外部服务成本和事件循环阻塞。
- **测试偏向边界场景**：覆盖了空查询、注入、解析失败和超时，而不是只覆盖成功路径，这是较好的测试倾向。

### 架构观察

- 成员加入审核是多阶段管线：本地黑白名单/词库 → LLM 初审 → 外部搜索 → LLM 复审 → 自动动作或人工处理。
- AstrBot 的搜索能力通过已注册工具复用，降低了自行管理客户端和密钥的成本，但也增加了对宿主平台 API、Schema 和异步返回协议的耦合。
- `membership.py` 承担了较多流程编排职责。随着搜索、复审、人工转交和日志继续扩展，建议将“搜索适配”“证据规范化”“审核决策”拆成独立边界，避免主流程继续膨胀。
- 自动处罚与外部证据之间存在明显信任边界：搜索结果只能作为参考证据，不能直接成为动作依据。

## 3. 规范完善建议

建议新增或强化以下审查规则：

1. **外部审核依赖必须具备完整降级契约**
   - 工具缺失、导入失败、超时、异常返回、空结果、解析失败均必须转人工；
   - 不得因搜索失败默认放行或拒绝；
   - 降级结果应带有可审计原因。

2. **外部内容必须视为不可信输入**
   - 搜索结果、网页标题、摘要和用户输入都必须与系统指令、审核规则严格分隔；
   - 应限制条数、长度、字符集和总 token 预算；
   - 测试必须验证证据中的“忽略前文”“直接通过”等指令不会改变审核协议。

3. **外部工具调用必须验证宿主协议**
   - 审查工具名称、注册方式、参数 Schema、同步/异步返回类型和真实异常行为；
   - 不能仅依赖 mock 证明兼容性；
   - 对关键工具至少增加适配层测试或集成冒烟测试。

4. **审核状态必须形成闭环**
   - 每个新状态都要有持久化、查询、展示、人工处理和重试路径；
   - 自动动作必须幂等；
   - 状态迁移和失败原因必须可审计。

5. **配置开关应测试组合语义**
   - 全局开关、分组开关、默认值、非法值和旧配置兼容性需要成组测试；
   - 配置关闭只应关闭搜索增强流程，不应跳过原有审核链路。

6. **时间预算应使用统一 deadline**
   - 单次查询、总查询、证据复审和整体审核流程共享明确的截止时间；
   - 取消超时任务，避免后台任务继续运行；
   - 测试应验证真实调用不会在超时后继续产生副作用。

## 4. 经验教训

- 在审核系统中，“无法判断”与“拒绝”必须严格区分。此次将搜索失败和复审失败转人工，是正确的安全边界。
- 采用三态或多态决策时，不能只检查解析是否成功，还要检查所有状态是否都有明确后继动作；尤其要防止未知字符串被错误映射成 `accept` 或 `reject`。
- 外部搜索结果不等于可信事实，也不等于审核结论。搜索只能提供证据，最终动作仍应受结构化复审结果和原有规则约束。
- 单测覆盖异常分支是必要但不充分的。对于 AstrBot 这种宿主平台集成，真实工具注册、异步协议和版本兼容性同样是关键证据。
- 日志不记录完整片段是好的隐私设计，但仍需记录查询数量、失败阶段、耗时、工具是否可用、最终降级原因和关联审核 ID，否则“可审计”可能不足。
- 搜索功能应防止成为资源放大器：每个加入请求可能触发多次外部查询和两次 LLM 调用，应考虑并发上限、全局速率限制、重复请求去重和缓存策略。

## 5. 增量审查反思

### 是否解决了之前的问题

历史上下文显示这是首次审查，且没有历史评论，因此不存在可验证的“已解决前置问题”。本次提交本身完成的是对搜索 fallback 的强化，而不是对既有审查意见的闭环修复。

### 是否引入新风险

新增风险主要来自外部搜索流程本身：

- 搜索工具协议或返回结构与假设不一致；
- 第二次 LLM 调用增加延迟、成本和失败面；
- 证据内容造成提示注入或上下文膨胀；
- 新状态未被所有人工审核、Dashboard 或持久化路径识别；
- 多个并发加入请求导致外部搜索和 LLM 请求放大；
- 搜索失败后虽能转人工，但可能缺少明确原因或重复进入审核队列。

目前没有证据表明这些风险已经实际发生，但它们是 approve 后最值得补充验证的项目。

### 增量范围导致的覆盖下降

增量审查天然容易只关注 `membership.py` 中新增 fallback，而忽略：

- 原有加入审核流程是否仍按正确顺序执行；
- 本地规则与新 LLM 分支是否重复处罚；
- 新配置是否正确接入 Dashboard 和持久化；
- 新状态是否兼容旧数据库记录和旧人工操作；
- 主入口、后台任务、API 入口是否共享同一套逻辑；
- 真实 AstrBot 版本下工具发现和调用是否成立。

因此，本次审查结论可以维持 approve，但后续应补充一轮非增量式回归审查，重点验证真实工具适配、状态闭环、配置组合、并发/取消和端到端人工转交。
