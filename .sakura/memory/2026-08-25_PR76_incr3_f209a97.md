## 2. 发现的模式

### 代码模式

从变更规模看，`index.html` 很可能存在以下一种或多种情况：

- 前端源码、模板和构建产物混合维护；
- 大量内联脚本或打包后内容直接提交；
- 构建工具导致格式化、压缩或换行变化，形成大 diff；
- UI 操作通过通用 HTTP 请求函数调用后端接口。

这类模式会降低审查可读性，并容易掩盖少量真实逻辑变化。后续应优先通过语义 diff、构建前源码或拆分提交审查，而不是把数千行删除/新增视为独立代码。

### 架构观察

项目包含审核链路、同步服务、远程动作和 Dashboard，属于“前端控制面 + 服务端状态 + 外部平台副作用”的架构。此类系统的风险不在按钮本身，而在跨层状态闭环：

- 前端展示状态不等于服务端权威状态；
- 服务端接受请求不等于远程动作成功；
- 远程动作成功不等于本地审计记录已正确落库；
- 前端隐藏按钮不等于权限控制；
- 建议动作必须绑定唯一记录，不能仅依赖群号、用户、文本等弱关联字段。

## 3. 规范完善建议

建议补充以下审查规则：

1. **大规模生成文件变更规则**  
   单文件重写比例较高时，必须确认是否为构建产物；要求提供源码 diff、构建命令和产物一致性验证。不能仅因业务逻辑改动很少而降低审查级别。

2. **前端动作安全规则**  
   对“应用、拒绝、删除、撤回、禁言”等按钮，必须检查：
   - 服务端鉴权和资源级授权；
   - 唯一动作/审核 ID；
   - 过期、重复和并发请求；
   - CSRF、XSS 和不可信文本渲染；
   - 服务端真实结果与前端提示的一致性。

3. **建议动作状态机规则**  
   建议至少区分 `pending / applying / applied / rejected / failed / expired`，并明确：
   - 谁是权威状态源；
   - 状态迁移是否合法；
   - 失败是否可重试；
   - 是否记录操作者、原因、时间和目标；
   - 远程动作与数据库状态不一致时如何补偿。

4. **增量审查证据规则**  
   增量审查必须记录：
   - 父提交与新增提交；
   - 受影响的后端接口和调用入口；
   - 相关旧测试及新增测试；
   - 未重新覆盖的历史风险；
   - 是否验证了构建产物和运行时路由。

5. **发布修复规则**  
   “修复打包”不能只看提交说明，应检查构建配置、产物清单、版本号、部署加载路径，以及干净环境下的构建和启动结果。

## 4. 经验教训

- **摘要不能替代 diff**：提交说明声称包含服务端动作，但实际变更文件只有 Dashboard，应先确认功能实现是否位于父提交，还是存在遗漏。
- **HTML 大 diff 需要特别警惕**：重排可能掩盖事件绑定丢失、接口参数变化、模板注入和兼容性问题。
- **前端成功提示必须以后端明确成功为准**：`200`、非空响应或请求发出都不能自动等同于动作成功。
- **远程动作必须可审计且幂等**：应用/拒绝操作应使用稳定 ID，并防止双击、刷新重放和多窗口并发。
- **外部动作失败不可默认成功或默认放行**：失败应显示明确状态，并提供人工处理或安全重试路径。
- **测试证据需分层**：前端按钮测试不能替代权限失败、服务端状态迁移、远程平台失败、重复请求和真实路由测试。
